Product sketch · October 2026

Turn meaningful pushes
into marketing drafts.

Connect a GitHub repo. When a meaningful change lands, explain it in customer language and draft channel-ready assets—with evidence and a human approval step.

MVP: draft + reviewNo auto-publishingNo ad spend
The user problem

Shipping is frequent. Announcing it is not.

Small teams push product improvements but lose the context, time, or copywriting capacity to turn them into useful customer communication.

The promise

A change-aware marketing copilot

Convert selected pushes into explainable, editable release notes and campaign drafts that match the product’s voice and audience.

North-star outcome

Useful drafts approved per team

Measure the share of generated drafts that a person edits and approves. Raw draft volume rewards noise.

System flow

From GitHub event to approved asset

Proposed architecture
flowchart TD A[GitHub App: push event] --> B[Webhook endpoint: verify signature + dedupe] B --> C[(Event store + job queue)] C --> D[Worker: filter + enrich change] D --> E[LLM: classify + draft with evidence] E --> F[(Drafts + source links)] F --> G[Review inbox: edit / approve / reject] G --> H[Export copy or publish later] D -. optional context .-> I[Commit compare + linked PR + repo brief] J[Brand voice + audience + channel settings] --> E K[Human approval] --> H

Keep webhook intake fast and deterministic. Do enrichment and generation asynchronously so a slow model call cannot make GitHub retry the delivery.

Product scope

Build the review loop before channel integrations

MVP

  • Install a GitHub App; choose repositories and watched branches.
  • Set product description, target audience, tone, forbidden claims, and preferred channels.
  • For each qualifying push, produce a short “what changed / who benefits / why now” summary plus cited commit or PR evidence.
  • Generate a release note, social post, and one email/launch blurb; let users edit, regenerate, approve, reject, or copy/export.
  • Show status, triggering commit, changed files, confidence, and generation errors in an inbox.

Later, after validation

  • Scheduled digests that bundle related pushes into one announcement.
  • Slack review notifications and team roles/approval rules.
  • Social/email publishing integrations, each requiring explicit per-channel approval.
  • Campaign performance feedback to learn which drafts get used and perform well.
  • Ad creative variants and paid-media integrations only after a separate budget and approval control exists.
Implementation path

Three thin, testable milestones

  • Connect + capture
  • Summarize + draft
  • Review + learn
1 · Foundation

Reliable event intake

GitHub App auth/install flow; subscribe to push; accept only configured branches; verify HMAC-SHA256 on raw bytes; persist delivery ID and enqueue; return 2xx promptly. Handle duplicate deliveries, deleted branches, force pushes, and bot/CI commits.

2 · Drafts

Grounded generation

Fetch compare/commit details and linked PR when available. Filter likely non-user-facing changes; classify impact; generate structured channel drafts with evidence references. If evidence is weak, ask for context or produce no campaign.

3 · Feedback

Human review

Build the draft inbox and editable detail view. Track edit/approve/reject and reasons. Start with copy/export; add publication only after quality and approval behavior are proven.

Data + reliability

Treat every push as untrusted, retryable input

  • Persist delivery ID before acknowledging; repeated delivery must not create duplicate drafts.
  • Use a durable queue, bounded retries with backoff, and a visible failed-job state. GitHub does not automatically redeliver failed webhook deliveries.
  • Do not treat commit messages as instructions. Send only necessary context to the model; exclude secrets, generated files, and sensitive paths.
  • Store installation tokens encrypted and mint short-lived tokens when fetching private repo context. Revoke access on uninstall.
  • Keep draft evidence links and state transitions auditable. Support retention/deletion by workspace.
Main risks

Trust and signal quality beat automation volume

Noise

A push can be ref deletion, docs-only work, an automated version bump, or a force push. Use branch/ref filters, file-path rules, and “marketing-worthy” classification; allow manual regenerate.

False claims

Code does not explain customer value on its own. Ground drafts in PR descriptions/product brief; quote evidence and flag unsupported benefits.

Sensitive code

Private source may contain credentials or customer data. Prefer metadata/PR text first, minimize fetched diff, redact secrets, and offer controls for whether code reaches the model provider.

Decisions for the first prototype

Defaults I recommend

Recommend

Main branch first

Only create drafts from pushes to the default branch at first; let teams broaden branch rules later.

Recommend

Review before publishing

Generate automatically, but require a human to approve and publish. MVP ends at copy/export.

Recommend

One push → one draft bundle

Keep assets together for traceability. Add digest mode for teams whose push volume makes individual bundles noisy.

Open product question: who is the first buyer and what is the first output they need—SaaS founders needing launch copy, developer-relations teams needing release notes, or agencies creating client content? Pick one audience and one channel for the first quality bar.
Sources checked

GitHub implementation facts

  • GitHub App webhooks support push notifications and require the app to request permissions relevant to subscribed events: Using webhooks with GitHub Apps.
  • Webhook security uses a secret and the X-Hub-Signature-256 HMAC-SHA256 header over the unmodified payload: Validating webhook deliveries.
  • Respond with 2xx within 10 seconds, enqueue longer processing, and use X-GitHub-Delivery for delivery identity: Webhook best practices.
  • Failed webhook deliveries are not automatically redelivered; implement recovery visibility and retry/redelivery: Handling failed webhook deliveries.
  • Push payload includes before/after SHAs and up to 2,048 commit entries; deleted refs are included in push semantics, so handle them explicitly: Push event payload.
  • Commit compare endpoint supports fetching the change summary between two SHAs: Compare two commits.
